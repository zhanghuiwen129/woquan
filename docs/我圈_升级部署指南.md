# 我圈 升级 / 代码更新部署指南

> [!WARNING]
> **当前架构仅支持单机部署（单台 Web 服务器 + 本机 MySQL + 本机文件存储）。**
> 这不是部署偏好，而是源码层面的硬边界：SSE 通知靠**本机文件 + flock**跨请求传递，且长连接直接占住 PHP-FPM worker；缓存默认落在**本机 `cache/` 目录**；上传默认写入**本机 `uploads/`**；在线升级会**直接覆盖本机代码目录**（不会同步到其它节点）；插件 `defer` 任务仍在**当前 PHP 进程内串行执行**。把同一份代码放到多台机器后面挂负载均衡，会出现事件丢失、缓存/限流不一致、附件只在某台机器可见、节点版本分裂。
> 需要先完成文末《多节点部署迁移清单》的全部改造并逐项验收，才可评估多节点部署；在此之前不要按多节点方式扩容。

> 配套文档：[搬家迁移指南](./我圈_搬家迁移指南.md)
> **搬家** = 整套换服务器 / 换域名；**升级** = 代码更新后同步到现有生产服务器。本文只讲升级。
> 适用对象：你的生产站点（及测试站点，如有）。若启用了授权站等附加服务，按其专属流程处理。

---

## 一、部署红线（绝对不能覆盖）

生产是**运行中的活环境**，以下文件/目录是各服务器自己的"身份信息"和"用户数据"，用 FTP 上传时**只传代码，绝不选这些**：

| 类型 | 路径 | 覆盖了会怎样 |
|---|---|---|
| 数据库配置 | `config.php`（根目录） | 全站 500，连不上库 |
| 用户上传 | `uploads/` | 所有图片/视频 404 |
| 缓存 | `cache/` | 可能因降级读取文件标记受影响；正常因 DB 优先不会重跑迁移，但两处标记都应保留（注意：`cache/.schema_version` 是迁移标记，别动） |
| 日志 | `logs/` | 覆盖无意义，且可能破坏写入权限 |
| 运行数据 | `data/`（授权站等） | 丢数据 / 授权失效 |
| 服务器配置 | `nginx.conf`、`.htaccess`、`web.config`、`Caddyfile` | 伪静态/安全规则被冲掉，整站 500 或暴露数据 |
| 安装锁 | 根目录 `.installed.lock`（旧版 `cache/install.lock`） | 首页 302 进安装向导或 404 |

> 同样**不要删**它们。只增/改代码文件（`api/`、`admin/`、`templates/`、`plugins/`、`scripts/`、`sql/`、`bootstrap.php`、`index.php`、`install.php`、`config.example.php`、`NOTICE`、`LICENSE`、根入口等）；实际清单以 `git diff` 为准。

## 二、方法一：FTP 客户端手动上传（推荐，最稳）

适合偶尔更新、或脚本被服务器限流时。

1. 用 FileZilla / WinSCP 连接你的服务器 FTP（传输模式必须选**二进制**）。
2. 本地代码根目录（如 `/path/to/woquan`），对照"本次改了哪些文件"，把对应文件/目录拖到服务器**同名路径**，弹窗选"覆盖"。
3. **只传代码目录**：`api/`、`admin/`、`templates/`、`plugins/`、`scripts/`、`sql/`、`bootstrap.php`、`index.php`、`install.php`、`config.example.php`、`NOTICE`、`LICENSE`（以 `git diff` 实际变更清单为准）。
4. 上传完**硬刷新**浏览器（Ctrl+F5）验证。

**如何知道"本次改了哪些文件"**：
```bash
# 上次部署基准到现在的全部变更文件（相对路径，直接对应 FTP 上传清单）
git diff --name-only <上次部署的commit或tag> HEAD

# 或：只看未提交的本地改动
git status -s
```
不确定基准时，直接把受影响目录（`api/`、`admin/`、`templates/`）整体覆盖即可——覆盖相同内容无害，比漏传安全。

## 三、方法二：脚本自动部署（curl 原子改名）

适合批量、或 CI。核心套路是**先传 `.new` 临时文件 → MD5 校验 → 原子改名覆盖 → 重列目录核验**，避免传半截导致白屏。

### 3.1 单次安全上传模板
```bash
FTP="ftp://你的FTP账号:密码@你的服务器地址:21"
LOCAL="/path/to/woquan"   # 你的本地代码根目录
f="admin/pages/categories.html"          # 要传的相对路径

# 1) 传 .new
curl -s --connect-timeout 25 -T "$LOCAL/$f" "$FTP/${f}.new"

# 2) MD5 校验（防半截）
L=$(md5sum "$LOCAL/$f" | awk '{print $1}')
R=$(curl -s --connect-timeout 25 "$FTP/${f}.new" | md5sum | awk '{print $1}')
[ "$L" = "$R" ] || { echo "MD5 不一致，中止"; exit 1; }

# 3) 原子改名（FTP 改名后连接可能被重置 exit 56，属正常）
curl -s --connect-timeout 25 -Q "RNFR ${f}.new" -Q "RNTO ${f}" "$FTP/"

# 4) 重列目录确认：原名在、.new 没了
sleep 1
curl -s --connect-timeout 25 --list-only "$FTP/$(dirname $f)/" | grep -qxF "$(basename $f)" && echo "OK"
```

### 3.2 批量脚本要点（踩坑后的正确姿势）
- **清单驱动**：把 `git diff --name-only` 的结果存成清单文件，逐行读取上传，不要整目录递归盲传。
- **降频 + 退避**：服务器有连接频率限制，**每文件之间 `sleep 3~5s`**，单文件失败重试 `sleep 15s`、最多 3~5 次。**不要高频密集请求**，否则会被限流（返回拒绝/超时），脚本会卡死在重试里。
- **中断可续**：已改名成功的文件下次重传会覆盖，无害；中断后重跑整份清单即可补齐。
- **临时文件清理**：若中途失败，生产可能残留 `xxx.new`，重跑会自动覆盖并改名，最终不应有 `.new` 残留。

> ⚠️ 经验：一次性密集上传大量文件可能触发服务器连接频率限制，导致脚本卡在重试里。建议降低上传频率，或改用 FTP 客户端手动上传。

## 四、后台前端改动的额外注意（极易"改了不生效"）

后台 `admin/` 的前端（JS/CSS）带了**版本参数缓存破坏**机制：
- `admin/index.html` 里 `main.js?v=`、`admin.css?v=`、`theme-boot.js?v=` 等
- `admin/js/nav-ui.js` 里的 `PAGE_VER`
- `main.js` 内部 `import './xxx.js?v='` 的模块 URL

**只要改了 `admin/js/*.js` 或 `admin/css/admin.css`，必须同步 bump 这些 `?v=` 版本号**（改一个数字即可），否则用户浏览器沿用旧缓存，表现为"明明传了新文件却没变化"。

> 注意：若后台菜单报"片段内容异常 / 缺少 #page-xxx 容器"，通常是 `admin/pages/` 下对应片段文件**未上传成功**（旧片段缺容器），不是缓存问题——先确认文件真的传上，再考虑 bump 版本。

## 五、部署后验证清单

部署后首次访问会自动执行增量数据库迁移（`index.php:130` 与 `api/index.php:112` 的 `Migration::run()`），当前最新为 V102（`MigrationBatchC.php:migrate102`），新增 `plugin_states` / `plugin_configs` / `pages` 三表，并为 `jobs` 增加 `priority` 优先级列与 `status='dead_letter'` 死信状态。迁移失败会落巡检标记 `cache/.migration_failed`，可用 `/health` 端点核对状态。

- [ ] 首页 / 动态列表正常打开
- [ ] 后台 `/admin/` 能登录，点各菜单无"片段内容异常 / 缺少 #page-xxx 容器"报错
- [ ] 图片 / 附件能显示（`uploads/` 未动）
- [ ] 改了的后台功能真的生效（必要时 Ctrl+F5 硬刷，或确认 `?v=` 已 bump）
- [ ] 关键 API 行为正常（如之前修过的 router / CSRF 相关接口）
- [ ] `logs/` 下无新增报错

## 六、回滚

代码回滚 = 把上一个稳定版本的对应文件重新传回生产（或 FTP 客户端用站点的文件历史/备份）。
数据回滚 = 用 `backups/` 下的数据库备份恢复（不要动 `backups/` 目录本身）。

## 七、代码版本管理（与部署区分开）

- **部署** = 把文件传到运行中的服务器（本文第一~六节）。
- **版本管理** = 用 Git 等工具管理源码、打 tag、记录变更。建议每次部署前用 `git tag` 或记录 `commit` 作为"已部署基准"，方便按 `git diff --name-only <基准> HEAD` 提取变更清单（见第二节）。
- 对外发布请遵循仓库的 `LICENSE` 与 `NOTICE`：本项目基于 Apache-2.0 再品牌化，需保留 `LICENSE`、`NOTICE` 以及上游文件头的"已修改"标注，对外不把上游项目名当作自己的商标使用。

## 八、多节点部署迁移清单（完成前请勿多节点上线）

> 本节是**迁移清单**，不是当前能力说明。下面 7 项全部完成、并在预发环境做过多节点对账后，才能把"仅支持单机"的边界解除。每一项都写清了「为什么要改」与「不改的后果」。

### 1. 缓存改 Redis（含失败告警）

- **为什么要改**：`Cache` 默认走本机 `cache/` 文件驱动；限流计数、登录失败锁定、配置与状态缓存都是本机可见。多节点下每个节点各算各的，限流阈值实际放大 N 倍，节点 A 清缓存不会影响节点 B。
- **不改的后果**：同一账号在节点 A 被限流、换到节点 B 又放行；后台改配置后部分节点长期读旧值；`plugin_states` 读缓存与 DB 不一致的窗口被放大。
- **怎么做**：统一设置 `CACHE_DRIVER=redis` 并配置 `CACHE_PREFIX`；确认所有节点指向同一 Redis 与同一前缀；把 `Cache.php` 中「Redis 连接/写入失败静默降级到文件」的分支改成**告警 + 显式失败策略**（至少记录带 `@allow-error-log` 标记的错误日志并接入监控），禁止多节点环境无声退回文件缓存。上线后用同一 key 跨节点读/删做一致性验收。

### 2. 分布式锁（Redis Lua，已有基础能力）

- **为什么要改**：文件驱动下 `Cache::withLock()` 用 `flock` 锁本机文件，只能互斥同一台机器上的进程；SSE 事件分发、限流回源、`remember` 单航班都会跨节点重复执行。
- **不改的后果**：同一事件被多个节点重复推送、同一回源被放大 N 次；临界区写入出现竞态，`jobs` 认领之外的计数器可能双加。
- **怎么做**：复用 `Cache::withRedisLock()` 已有的 NX/PX + Lua 安全释放实现（不要另造锁），确认所有 `withLock()` 调用点在 Redis 驱动下走的是该分支；给锁等待/续期失败加指标与告警；严禁把锁 TTL 当成业务幂等保证，业务侧继续保留唯一键/dedupe_key 幂等。

### 3. 上传改共享对象存储

- **为什么要改**：默认上传驱动是 local，文件写在节点本机 `uploads/`，并通过本地 Nginx/Apache 静态目录对外提供。
- **不改的后果**：用户在节点 A 上传的图片，请求落到节点 B 时 404；头像/附件、水印原图出现"有时能看到有时看不到"；扩容时新节点没有历史文件。
- **怎么做**：统一切到 OSS/COS/七牛等对象存储驱动（后台设置里已有 `upload_driver` 及对应密钥项），所有节点使用同一 bucket + CDN 域名；把 `uploads/` 仅保留为降级/本地开发用途并禁止在多节点写；迁移历史文件到对象存储后，逐类抽检图片、视频、附件 URL 在各节点均可访问。

### 4. SSE 改独立网关 / 长连接服务

- **为什么要改**：当前 SSE 用本机文件 + `flock` 做跨请求事件传递，并在 API 请求里直接持有 FPM worker 等待推送；源码注释已明确约 20 个并发连接就能耗尽 worker 池。
- **不改的后果**：多节点下订阅落在 A、发布落在 B 时事件丢失；并发稍高即整站 504（不是 SSE 单独降级，而是 FPM 池被打满）；横向扩容只能线性放大 worker 成本。
- **怎么做**：把 SSE 从 PHP-FPM 移出，改为独立长连接服务（如网关 + Redis Pub/Sub 或 WebSocket 服务），PHP 侧只负责鉴权后发布事件；保留 `last_event_id` 续传语义与事件格式；先做灰度：新旧双写、客户端对比无差异后再摘掉本地文件通道。上线前压测并发连接数与内存曲线。

### 5. cron 集中化（避免多机重复执行）

- **为什么要改**：`/api/cron/*`、`/api/cron/jobs` 等任务目前依赖站点侧定时触发；多节点若每机都配一份 crontab，同一任务会执行 N 次。
- **不改的后果**：圈子订阅清理、jobs 消费、归档/统计重复执行；即使有 dedupe_key 也会放大数据库压力，非幂等任务直接产生重复数据/重复通知。
- **怎么做**：只在一台专门的任务节点（或一个带领导选举的调度器）配置 cron，并在入口加「cron_secret + 节点白名单」双校验；其余 Web 节点禁止外部访问 cron 路由；用执行日志与 `jobs` 表行数验证每天每个任务只跑一次；任务节点故障时明确告警，而不是让多台机器盲跑。

### 6. `uploads/` / `cache/` / `logs/` 目录：共享还是本地化，必须写清楚

- **为什么要改**：升级脚本会覆盖本机目录，在线升级也只改本机代码；`cache/` 里还有迁移标记 `.schema_version` 等本机状态；`logs/` 多机混写会让排障失去顺序。
- **不改的后果**：用 NFS 把 `cache/` 共享给多节点会让 `flock` 在跨机文件系统上语义不确定、甚至锁失效；把 `logs/` 共享会掩盖是哪台节点出错；误把 `uploads/` 当"代码"覆盖会直接丢用户文件（见第一节部署红线）。
- **怎么做**：`cache/`：多节点切 Redis 后仅作单节点降级目录，**不共享**，并在监控上禁止多节点同时使用文件驱动；`uploads/`：优先对象存储，若短期仍用本地盘则必须挂只读共享存储且写入走单一上传节点，禁止部署脚本覆盖；`logs/`：每节点本地写、统一采集到日志平台并带节点标识；`data/`、`.installed.lock`、`config.php` 每节点各自保留，不允许跨节点同步或覆盖。发布时所有节点必须走同一份代码清单与版本号，并在升级窗口内禁止"部分节点新版本"对外服务。

### 7. 容量告警（SSE 并发、FPM `pm.max_children`）

- **为什么要改**：单机时代的容量天花板由 FPM worker 数决定，SSE 又直接占用 worker；没有指标时瓶颈只会以随机 504 暴露。
- **不改的后果**：连接数上涨时整站不可用且无法区分是 SSE 占池还是业务慢查询；扩容加机器也无效（事件仍走本机文件，问题只是被复制）。
- **怎么做**：至少接入两组告警：①活跃 SSE 连接数 / 推送延迟 / 事件积压，达到 `pm.max_children` 的 50% 即预警、70% 即限流新连接；②FPM 池使用率、队列等待时长与 504 速率，持续 1 分钟超阈值即触发；同时监控 Redis 连接失败率与对象存储 5xx（前 3 项改造后的新单点）。在单节点上先跑一次容量基线压测，把告警阈值写进部署记录，再逐步扩节点。

## 九、发布单模板（发布纪律）

> **纪律：无 tag 不得发布。** `php scripts/check-release-version.php` 只做只读校验：无 tag / CI 无 `config.php` 时按 WARN 跳过（退出码 0，不阻断流水线，避免源码包检出误伤）；但只要 tag 与 `APP_VERSION` 不一致，或 `Migration::$currentVersion` 不是正整数，立即 FAIL（退出码 1）。因此**脚本 WARN 不等于允许发布**，正式发布必须人工确认下表全部勾稽完成。

### 9.1 版本号三值（2+1 勾稽）

**三条定稿口径（2026-11-26）**：① tag 格式固定 `vX.Y.ZZ`（两位补零，与 `config.example.php` / `install.php` 的 `v2.17.00` 一致）；② Migration 版本保持独立，不与 APP_VERSION 数值对齐；③ 脚本 WARN 保持退出码 0、不升级为 FAIL——CI 源码包检出无 `.git` 与安装生成的 `config.php`，升级会让所有源码包检出的流水线误报失败；WARN ≠ 允许发布，须由 §9.6 人工签核。

| 项 | 真源 | 本次值 | 勾稽要求 |
| --- | --- | --- | --- |
| git tag | `git tag --points-at HEAD`（发布机上） | `v____` | 格式固定 `vX.Y.ZZ`；与 APP_VERSION 去**单个** `v/V` 前缀后字符串严格相等——脚本不做数值归一，`v2.17` ≠ `v2.17.00`。发布前打 tag，脚本只读、不创建 git 对象 |
| APP_VERSION | `config.php:17` 的 `define('APP_VERSION', '...')` | `v____` | 与 tag 一致；`config.php` 是安装程序生成、禁止入库，**FTP 升级不得覆盖**（发布前确认发布机已同步，必要时由 `Upgrade::syncLocalVersion` 写入） |
| Migration 版本 | `api/core/Migration.php` 的 `$currentVersion` | `V____` | schema 维度，**不要求与 APP_VERSION 数值相等**，但必须是合法正整数并记入发布单 |

> 实战坑：仓库里的 `config.example.php` / `install.php` 是 `v2.17.00`，但已有站点的 `config.php` 可能停留在旧版本（本机实测为 `v2.16.29`）。若按示例版本打 tag 而发布机 config.php 未同步，校验会以 `VERSION_MISMATCH` FAIL——打 tag 前先跑一次下面的只读命令确认实际值。

校验命令（只读，可在任意环境跑）：

```bash
php scripts/check-release-version.php
php scripts/check-release-version.php --json      # CI / 归档用，status = pass | warn | fail
```

### 9.2 变更与迁移

- [ ] FTP 变更文件清单：`git diff --name-only <上一稳定 tag> HEAD`，逐文件确认已上传（尤其 `admin/pages/` 片段文件，漏传会报"缺少 #page-xxx 容器"）
- [ ] 明确排除不得覆盖项：`config.php`、`.env`、`data/`、`uploads/`、`cache/`、`logs/`、`.installed.lock`（见第一节红线）
