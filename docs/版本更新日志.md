## 1. 版本标识

| 项 | 位置 | 当前值 |
| --- | --- | --- |
| 服务端版本 | `config.php` / `config.example.php` 的 `APP_VERSION` | `v2.16.29` |
| 数据库迁移版本 | `api/core/Migration.php` 的 `$currentVersion` | `101` |
| 迁移记录 | `schema_versions` 表 | — |
| 客户端版本 | 后台「App 版本」管理的 `app_versions` 表 | 按平台分别配置 |

| 版本类型 | 格式 | 递增规则 |
| --- | --- | --- |
| 服务端 | `v2.16.<patch>` | 每次发布递增 |
| 迁移 | 整数 | 每次新增 `migrateNN()` 递增 |
| 客户端 | `version_code` 整数 + `version_name` | 按 `android` / `ios` / `h5` 分别维护 |

### `GET /app/version`

| 参数 | 值 |
| --- | --- |
| `platform` | `android`（默认）/ `ios` / `h5`；非法值回退 `android` |
| `code` | 客户端当前 `version_code`，默认 `0` |

| 响应字段（`data`） | 说明 |
| --- | --- |
| `has_update` | `version_code > code` |
| `force` | `has_update` 且 `update_type === 1` |
| `version_name` | 版本显示名 |
| `version_code` | 最新版本号 |
| `changelog` | 后台填写的更新说明 |
| `download_url` | 下载地址 |

无已启用版本时返回 `{"has_update":false,"force":false}`。结果按平台缓存 300 秒。

```bash
curl -s 'https://example.com/api/app/version?platform=android&code=160'
```

## 5. 升级与回滚

### 5.1 升级步骤

| # | 操作 |
| --- | --- |
| 1 | 备份数据库与代码，确认 `backups/index.json` 生成了可用记录 |
| 2 | 上传 `api/`、`templates/`、`admin/`，保留 `config.php`、`uploads/`、`cache/`、`logs/`、`backups/` |
| 3 | 触发一次 `/health` 或任意 API 请求，由 `Migration::run()` 执行增量迁移 |
| 4 | 删除 `cache/*.cache` 与 `cache/.schema_verified`，重跑一次请求 |
| 5 | `php scripts/build_migration_contract.php --check` |
| 6 | `php api/tests/run_tests.php`、`node scripts/audit-theme.js` |
| 7 | 后台 JS 改动后同步 bump 6 处缓存指纹，再复测后台页面 |
| 8 | 复测 `/health`、登录、发帖、支付回调、SSE |

### 5.2 保护清单

| 不覆盖 | 原因 |
| --- | --- |
| `config.php` | 含数据库凭据与 `JWT_SECRET` |
| `uploads/` | 用户上传文件 |
| `cache/` `logs/` `backups/` | 运行时数据与备份 |
| `license_system/data/` | 授权 RSA 私钥，nginx 已 deny；仅独立授权站场景存在 |

### 5.3 回滚

| # | 操作 |
| --- | --- |
| 1 | 在 `backups/index.json` 中确认目标记录的两个备份文件存在 |
| 2 | 后台 `POST /api/admin/rollback` |
| 3 | 系统先恢复数据库、后恢复代码；升级失败时自动执行同样顺序 |
| 4 | 清 `cache/*.cache`，复测 `/health` |
